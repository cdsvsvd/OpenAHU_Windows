# 成员04业务层代码评审与兼容合并（4.zip）

## 1. 代码审查范围
成员04提交了独立的 OpenAHU.Application，包括业务领域模型、8个仓储接口与IUnitOfWork、7个查询服务、课程增删改命令、字段校验、周次规范化以及README/HANDOFF。该交付说明明确表示**未执行.NET编译，未提供单元测试**。这些是交付物原文声明，不能视为CI已通过。

## 2. 与当前main已经存在的冲突
- 当前已采用 \`ICampusService + ICampusRepository\`，\`Application\`引用冻结的 \`Contracts\` 数据传输对象；04号提供 \`ICourseCommand/ICourseQuery\` 等接口和自己的一套Model，不能直接替换，否则API和5号Repository不匹配。
- 04号新增课程使用 \`course-local-\` 前缀；当前 \`/api/v1/local/courses\` 写入成功的ID是 \`local-\` 开头，并在5.1版本中加了本地课程修改权限检查。修改前缀会使编辑/删除新课程被拒绝。
- 04号建议POST/PUT/DELETE统一200并返回 \`CourseWriteResponseDto\`，但当前固定为POST 201返回 \`CourseDto\`、PUT 200返回 \`CourseDto\`、DELETE 204。不能静默改变前端对接协议。
- 04号 \`CourseCommand.UpdateAsync/DeleteAsync\`在\`FindAsync(courseId)\`之后缺少验证课程属于当前活动学生且为个人可编辑课程；允许修改其他用户课程或共享课程的语义与团队现有的权限约束相反，存在越权、共享数据误改风险。
- 04号将排课冲突标记为400，而当前稳定后端为409；同时其文字字段上限为60/40/60，当前合同与业务层使用120/100/150。不得不经评审直接变更。
- 04号CRUD预读在写事务外，可能被并发请求改变前提。当前基础版Create/Update也有同类竞态风险，此次进行修正。

## 3. 本次已吸收和完善的内容
- 参考04号纯函数\`CourseWriteValidator\`的思路，新增 **Application层无数据库依赖** 的字段校验类，保留冻结请求DTO、字段长度、400状态与错误JSON格式，明确输出name/teacher/location/dayOfWeek/startSection/endSection/weekNumbers，便于前端定位。
- 输入字符串按实际入库的Trim值判断最大长度；教师和地点允许空字符串，但遵守当前DTO不可为JSON null的约束；周次拒绝重复、越界与空列表。
- 在Application里检查学期存在性和week_count；在Infrastructure里根据活动学生、学期、星期、节次和共同周次检测排课冲突，错误含冲突课程名称。坚持409，避免破坏当前API调用者。
- 将Create/Update的排课冲突、课程归属、成绩/考试关联保护等检查纳入同一个SQLite写事务，减少并发写入时的检查-写入窗口。
- 扩展Windows真实HTTP烟测：空白课程名、教师超长、星期越界、节次非法、重复和越界周次、未知学期、实际课程冲突，验证失败操作没有写入数据；验证成功创建时Trim处理。
- 原有5.1的个人课程写权限、共享课程保护、原子删除、数据库健康检查及数据库迁移历史不变。
