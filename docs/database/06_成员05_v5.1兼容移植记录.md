# 5号同学5.1版本：兼容性审查与移植记录

## 输入与目标
输入包：用户上传 `5.1.zip`，含成员05独立Infrastructure、对应成员04 Application版本、数据库工具与57项测试记录。
当前项目：以已通过Windows GitHub Actions的`main`为基线，继续采用现有`ICampusService/ICampusRepository`、11条API和SQLite迁移编号`202611050001_InitialLocalDatabase`。

## 已吸收的功能
- 课程周次写入：编辑时对已跟踪周次脱离跟踪，使用单事务批量删除旧周次并插入新集合；覆盖同一课程连续编辑周次且有重叠键的场景。
- 删除安全：`ExecuteDeleteAsync`使用同一SQL原子条件同时检查学生关联、其他学生关联、成绩与考试；避免在预检查后新产生的关联记录被级联删除。保留409冲突语义。
- 权限边界：仅允许`local-*`课程通过本地维护API修改，原有演示种子课程及非本人课程无法被此入口修改。
- 数据库健康：活动学生设置必须关联实际学生；现有已管理SQLite库在迁移前执行只读`quick_check`和`foreign_key_check`。
- 回归测试：Windows HTTP烟测增加重复周次编辑、演示课程保护、孤儿活动学生、错误外键数据库拒绝启动场景。
- 演示链接：新建库中的项目链接更新为当前`cdsvsvd/OpenAHU_Windows`仓库。

## 未直接合并的5.1文件与理由
- 5号携带的整个`OpenAHU.Application`源自04交接包，不等于主分支的Application。直接替换会更改现有调用契约，无法保证3号和前端代码正常运行。
- 5号独立的8个Repository与`IUnitOfWork`需要另一套`OpenAHU.Application.Abstractions`；当前项目用统一`ICampusRepository`，不混合两套接口。
- 5号首个迁移`20261105071817_InitialCampusSchema`不能取代现有`202611050001_InitialLocalDatabase`，否则可能使旧数据库迁移历史断裂。
- 5号的`57项通过`是其交付记录，不自动等同于本仓库的CI。这里使用当前Windows Actions中的编译与真实HTTP烟测作为合并门槛。
- 5.1使用EF Core 10.0.11，低于当前仓库10.0.14；不回退依赖版本。

## 仍需团队后续讨论
- 正式EF模型快照再生成并恢复PendingModelChangesWarning检查；当前手工迁移先保持兼容，避免修改已经部署的SQLite。
- 并发写入仍需更完整的多进程压力测试、数据库备份恢复和SQLite锁竞争测试。
- 6人团队如果决定全面采用5号/4号的独立仓储与UnitOfWork，应另开架构迁移PR，并明确新旧API DTO与迁移历史之间的映射，不能混入本次兼容性修复。
